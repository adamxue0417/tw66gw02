# main 固件编码规范

适用于本项目自行维护的业务代码、Bootloader 和构建工具。目标是便于查找、修改和复核，并保持已有固件行为可追溯。

## 1. `.h` 与 `.c` 的分工

| 内容 | 放置位置 | 本项目示例 |
| --- | --- | --- |
| 对外函数声明、跨模块类型、协议码 | 对应模块的公共 `.h` | `COP/ota_update.h` 的 OTA 类型、状态及原因码 |
| 可维护的阈值、采样数量、周期参数 | 模块配置头文件 | `BSP/temp_config.h` |
| 私有状态类型、内部缓冲区配置、存储记录格式 | `模块名_internal.h`，仅本模块实现包含 | `COP/ota_update_internal.h`、`COP/main_control_internal.h` |
| 函数实现、变量实体、查找表 | `.c`；仅本文件使用时加 `static` | OTA 会话变量、温度查找表 |
| 对外共享变量声明 | 公共 `.h` 使用 `extern`，仅一个 `.c` 提供实体 | 遥测调试信息 |

**定义写在 `.c` 中并不天然违反 C 语言规范。** 本项目将需要集中维护的模块宏和类型整理进头文件；不要把变量实体、普通函数实现和大型 `static const` 表搬进头文件，也不要为只在函数内使用的局部变量创建头文件。

私有头文件不是公共接口。其他模块通过公开函数访问状态，不能包含 `*_internal.h` 直接操作内部记录。不要把所有定义堆入 `config.h`。

## 2. 头文件与命名

- 新头文件使用唯一保护宏，例如 `MATHIS_OTA_UPDATE_INTERNAL_H`；避免双下划线等实现保留标识。
- 新头文件直接包含所需类型的依赖；应能单独包含，也能重复包含。禁止包含 `.c` 文件。
- 现有 `config.h` 存在历史聚合依赖，新模块不再增加相互包含。改造依赖时单独验证，不能顺手重写整个工程。
- 新宏使用模块前缀和大写下划线；常量表达式加括号，无符号量使用 `u`。已有宏名按兼容性逐项整理，不能盲目全局替换。
- 时间、温度、电压等名称注明单位或调度周期，如 `_TICKS_20MS`、`_TICKS_100MS`、`_MV`、`_C`。注释注明测量口径，不能凭名称猜测单节或整组电压。
- 函数声明与定义保持类型一致；无参数函数写 `(void)`；删除重复声明。公共返回码写入公共头文件，例如 `SCH_RETURN_NORMAL` 和 `SCH_RETURN_ERROR`。

## 3. 参数、协议与内存

- 一个参数只设一个来源；Bootloader 与应用的 Flash 分区共用 `ota_layout.h`，禁止复制地址后分别维护。
- 区分编译开关的“是否定义”和数值开关。现有 `SCH_REPORT_ERRORS` 使用 `#ifdef`，写成 `0` 仍会启用；如改变开关语义须单独修改使用点并验证。
- 宏不能多次求值有副作用的参数；复杂操作优先函数。保留寄存器的 `volatile` 语义。
- 协议字段、持久化结构的字段顺序、类型和对齐是兼容性约定；仅整理文件时不得改变。不能将 `uint8_t` 字段随意改为 `enum`。
- 缓冲区、任务数量、栈和堆的调整必须核对 RAM/Flash 预算；中断共享状态除 `volatile` 外仍须考虑原子性和竞争。
- 整理定义位置不改变参数值：当前温度/电量阈值、超时、队列深度、版本号与签名策略保持原值。新的产品要求另行验证。

## 4. 文件维护与验证

- 一次提交集中解决一个问题，避免混入功能修改、全文件格式化和编码转换。新文件使用 UTF-8；编辑旧文件保留既有文字编码及未改动内容。
- ST HAL/CMSIS、厂商时钟模板和独立诊断程序按其原有约定维护，不为消除 `.c` 中所有宏而批量修改厂商代码。
- 改头文件后执行干净工厂构建、v100/v101 OTA 构建和现有产物测试，检查错误/警告、布局、CRC 和文件哈希。
- 对纯组织重构，优先验证构建出的 Bootloader、应用和交付文件与原基线一致；如不一致，先解释差异，不能直接更新基线掩盖问题。
- 编译和主机模拟不能代替实机验收。已交付压缩包和冻结固件不覆盖；新源码交接使用新包名。
